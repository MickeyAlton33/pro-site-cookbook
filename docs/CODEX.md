# Codex setup and verification

The same `skills/pro-site` folder serves Claude Code and Codex. Codex loads its own
plugin manifest, hook command, and project instructions; it does not need Claude
Code installed. Tested with Codex CLI 0.169.0. Older clients can use the standalone
skill when they lack `codex plugin` support.

## Install, update, remove

From the repository root, `bash scripts/install-codex.sh` registers this local
marketplace and installs `pro-site@pro-site-cookbook`. Start a new session. To install
a released checkout remotely:

```bash
codex plugin marketplace add MickeyAlton33/pro-site-cookbook
codex plugin add pro-site@pro-site-cookbook
codex plugin list
```

After upstream changes, run `codex plugin marketplace upgrade pro-site-cookbook`,
then `codex plugin add pro-site@pro-site-cookbook` and start a new session. For a local
marketplace, rerun `bash scripts/install-codex.sh` after pulling changes.
Remove with `codex plugin remove pro-site@pro-site-cookbook` and optionally
`codex plugin marketplace remove pro-site-cookbook`.

Plugin hooks require Codex's hook trust review; installation does not bypass it.
Use `$pro-site:pro-site` (plugin) or `$pro-site` (standalone) or normal implicit skill selection if the hook is unavailable or
untrusted. Hooks are not guaranteed on every Codex/ChatGPT surface. This workflow
needs a local shell/filesystem and a browser; it is not a hosted website builder.

For the IDE or standalone skill discovery (choose this **instead of** the plugin):

```bash
bash scripts/install-codex.sh --skill
# Repository-only alternative, run from this cookbook checkout:
bash scripts/install-codex.sh --skill /absolute/target-project/.agents/skills
```

The installer symlinks the complete skill (scripts/templates/references included),
refuses conflicting destinations, and can be rerun safely. Keep the source checkout.
`git pull --ff-only` updates a symlink install. Remove only the installed symlink to
uninstall. No global `AGENTS.md`, model, permissions, or unrelated MCPs are changed.

## Use

In a new session outside an existing web project:

```text
$pro-site:pro-site Design a landing page for my coffee roastery.
```

Expect the mode question, then three directions after choosing Pro-site. You can
preselect: “Use Pro-site for a coffee roastery site at /my/path.” An existing mode,
brief, or direction is reused. Without a question UI, the agent asks in plain text
and waits. Edits inside an existing site proceed directly.

The agent runs `new-site.sh --agent codex <path>`. `--agent both` wires both clients;
no option retains the original Claude default. `AGENTS.md` is the single editable
contract and includes any framework rules generated by Next.js. `CLAUDE.md` imports
it, so decisions stay consistent when switching agents.

## MCP setup and fallbacks

The Codex scaffold writes **project-local** `.codex/config.toml` for shadcn,
Context7, and headless Playwright. Codex loads project config only after the project
is trusted. Open a new session in the generated directory and check `/mcp` or
`codex mcp list`. A project created during an existing session does not inject its
MCPs into that session: use the shadcn CLI, official docs, and generated Playwright
scripts immediately, then restart when useful.

To add optional project tools, run this from the generated project, using the
absolute installed skill path for `<skill>`:

```bash
bash "<skill>/scripts/add-mcp.sh" --agent codex chrome-devtools figma vercel
# Also supported: shadcn context7 playwright 21st fal webflow framer
```

This preserves existing server entries, appends missing ones, and never writes
OAuth secrets. For custom inline TOML layouts it stops without changing the file;
merge those manually. For authenticated HTTP servers, run `codex mcp login <name>`
from the project after trusting it. Provider accounts/consent may be required;
authentication and paid generation cannot be assumed. Chrome DevTools needs Chrome.
The helper does not automatically authenticate or start billable provider jobs.

`codex mcp add` is a user-level convenience command; this cookbook deliberately
writes project TOML instead to avoid loading optional tools in every project.
The Claude `add-mcp.sh 21st|fal|webflow|framer` behavior is preserved.

## Browser review and quality gates

The reviewer checklist lives in `references/design-review.md` and is copied into
`docs/design-review.md` in every site. Codex uses a permitted reviewer when available
or performs a clearly labeled self-review. It never assumes the Claude agent or
Claude MCP tool names exist.

The generated scripts work without MCPs:

1. Start the dev server, then `npm run review:capture -- http://localhost:3100 /`.
   Open the six images in `.review/`; inspect `results.json` for errors. Add all
   real routes to the arguments. Check keyboard interaction and normal motion too.
2. Run lint and `npm run build`, then `npm run start -- --port 3200` in another
   terminal/process. Run `npm run test:lighthouse -- http://localhost:3200`.
   Reports are `.lighthouse/mobile.json` and `desktop.json`; either Performance or
   Accessibility below 95 makes the command fail. It audits an already running
   production server and leaves its lifecycle to the caller.
3. Add every route to `tests/visual.spec.ts`, generate snapshots, inspect them, and
   verify without `--update-snapshots`. Playwright starts/stops its own production
   server on 3300; set `PW_PORT` if occupied. It never reuses an unknown server.
4. Stop the dev/production processes you started. Commit reviewed baselines under
   `tests/__screenshots__/`; transient review and Lighthouse files are gitignored.

Use the same OS/browser versions for creating and comparing baselines. Lighthouse
scores vary with the machine and content; a scaffold smoke pass is not a guarantee
for a finished design. Field INP requires field data, not a Lighthouse claim.

## Maintainer validation

```bash
node --test tests/*.test.mjs
bash -n scripts/install-codex.sh skills/pro-site/scripts/*.sh
```

Offline tests cover client selection, paths with spaces, preserved framework and
Claude instructions, safe repeated MCP setup, refusal of existing destinations,
installer conflicts, English/Hebrew hooks, and no global Codex config writes.

Test packaging without changing your user setup:

```bash
validation_dir=$(mktemp -d)
CODEX_HOME="$validation_dir" codex plugin marketplace add "$PWD"
CODEX_HOME="$validation_dir" codex plugin add pro-site@pro-site-cookbook
CODEX_HOME="$validation_dir" codex plugin list
```

For a real smoke test, scaffold into a new temporary directory with `--agent codex`,
run lint/build, capture production screenshots, run Lighthouse, create and verify
visual baselines, and stop the server. Repeat client-specific wiring with `--agent
both` when changing that path. Dependencies and Chromium require network access;
provider OAuth is a separate interactive check.
